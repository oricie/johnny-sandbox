🔎 Critical alerts on crown-jewel assets are buried under duplicate low-severity noise in the alert queue

This hits the primary persona, the core job (triage), and the quarter's success metric directly. The queue's order ignores the two attributes analysts use to judge urgency, and the data needed to fix it is already in the API response.

Evidence
  • Median time to open a critical alert is 1260s against a 300s target, more than four times over. analytics.json#screens["/alerts"].events.time_to_open_critical_s
  • The quarter's success metric is mean time to triage for critical alerts on crown-jewel assets, with a target under 5 minutes. product.md
  • Analysts scroll a median of 46 rows before reaching a critical alert. analytics.json#screens["/alerts"].events.scroll_depth_before_critical
  • Analysts open a median of 38 alerts per session, and 64% of opened alerts are closed as duplicates within 20s. analytics.json#screens["/alerts"].events.open_alert
  • The 64% duplicate-close rate comes from the duplicate-close event. analytics.json#screens["/alerts"].events.close_within_20s_as_duplicate
  • Analysts spend a median of 2010s on the queue, versus 640s for incident leads. analytics.json#screens["/alerts"].by_role
🔒 Not changing
  • Analysts click the disabled 'Isolate host' button: This friction is deliberate under decisions.md#D-12. Enabling containment for analysts or removing the restriction is out of bounds.
Also noticed, for later
  • The containment restriction is explained only in a hover tooltip
  • PageHeader subtitle colour fails contrast and is hardcoded
  • Severity badges carry no severity styling

Before
Option A · Risk-ranked queueRecommendedlow risk

Change the queue's order so that it reflects urgency instead of arrival time. AlertList sorts by severity rank, then assetCriticality rank (crown-jewel > production > internal > test), then detectedAt descending. An Asset column shows asset name plus criticality. Severity renders as a Badge with a severity variant built on the --color-sev-* tokens, keeping the severity word visible. Critical rows on crown-jewel assets get the --color-sev-critical-bg background. Every alert remains a row, so nothing is hidden or closed.

  • Targets the quarter's metric directly: critical crown-jewel alerts land in row 1 whatever the noise volume.
  • Matches how the primary persona judges urgency: severity plus asset.
  • Every raw alert stays visible as its own row, fully compliant with D-07.
  • Uses the existing Table, Badge and sev tokens, so the change is small and contained.
  • Duplicate noise is still present lower in the list, so the 64% duplicate-close rate will improve only indirectly.
  • Relies on the Alert type in protected demo-app/src/api/types.ts exposing asset and assetCriticality. The API returns them, but the type cannot be edited if it lacks them.
  • Analysts used to strict chronological order may need a visible sort indicator.

Option B · Collapse duplicates by fingerprintmedium risk

Reduce noise volume instead of reordering. AlertList groups alerts sharing a fingerprint into one summary row showing title, asset, a count (for example, '×5') and latest time. The row is styled with --color-row-muted and can be expanded to list every underlying raw alert. AlertQueue's subtitle reports both totals (for example, '10 alerts · 6 groups') so nothing appears to be missing. Groups keep chronological order by latest occurrence.

  • Attacks the duplicate-open waste directly (38 opens per session, 64% closed as duplicates).
  • Shortens the list substantially when one noisy source repeats.
  • Grouping is explicitly allowed by D-07 as long as raw alerts stay reachable.
  • A critical alert still sits wherever its timestamp puts it, so a burst of distinct low-severity alerts can still bury it, and the metric gain is indirect.
  • Collapsed groups risk looking hidden to an auditor unless expand and counts are very clear (D-07 sensitivity).
  • Needs expand/collapse state and row-nesting inside Table, which makes it more complex to build.
  • Relies on fingerprint being exposed in the protected Alert type.

Recommendation: A. The quarter is judged on time to triage critical crown-jewel alerts (product.md), and median time to open a critical alert is 1260s against a 300s target (analytics.json#screens["/alerts"].events.time_to_open_critical_s). The root cause is that AlertList.tsx orders only by time. Option A puts the most dangerous alerts first regardless of how much noise exists, and keeps every raw alert visible per D-07, at low risk. Option B reduces noise but leaves critical alerts positioned by timestamp; it is a good follow-up once ranking is in place.
